# ADR 0006: Tenant configuration persistence increment

Date: 29 October 2026
Status: Implemented and validated locally against PostgreSQL 17.2; awaiting owner review

Keep the existing lightweight Domain/Application/Infrastructure boundary. Do not modify the pure Evaluation assembly, add shared framework dependencies, or build M3/M4/M5 features. This increment implements application operations and persistence adapters; an HTTP composition host and provider reads remain a later reviewable increment.

AuthenticateTenant validates the Forge token first, then resolves an exact enabled app/environment/installation/cloud binding from an operator-only directory. Actor comes from the verified token. Empty identities, unknown installations, invalid roles, mismatched repository tenants and absent grants fail closed. TenantIdentity has validated immutable fields. Application services receive one fresh tenant-bound repository/context per operation; they never accept a request-selected tenant.

SystemAdministrators in the authenticated organization manage tenant-wide catalogs and delegation. EvaluationManagers manage profiles only in explicitly granted organization/team/project scopes. Scoped managers may use inline metric definitions in their profiles; tenant-global catalog mutation requires administrator authority. Developer/Reviewer grants confer reads only. Profile management never implies repository access. Scope existence/provider entitlement validation remains necessary before Jira integrations are exposed.

EF Core global filters apply to every configuration entity. Composite tenant/entity primary and foreign keys protect relationships. Save guards reject foreign-tenant writes, immutable updates/deletes and unsupported lifecycle transitions. PostgreSQL adds FORCE row-level security to configuration tables, with tenant identity set on every newly opened connection, and database triggers protecting immutable history even through raw SQL. The installation directory is intentionally outside tenant CRUD and queried only by the exact verified tuple. Production application roles must not be superusers, bypass-RLS roles or schema owners with DDL privileges; local schema installation uses a separate explicit operator action and refuses superuser/bypass-RLS roles.

Metric versions, catalog versions/selections and profile contents are append-only. Catalog snapshots own exact metric contents and relational references to retained versions. Profiles own complete M1 snapshots and content hashes; the application verifies catalog provenance rather than trusting a supplied reference. All content changes create new versions, including drafts. Lifecycle and assignment revisions use optimistic concurrency; unique version and active-scope indexes reject races. A conflicting active profile must be explicitly archived before activating a replacement. Assignment is a separate explicit operation and requires an active profile in the exact authorized scope. Broader-scope reuse and project/team/organization effective resolution remain deferred.

Configuration changes and append-only audit events share one SaveChanges transaction. Failed units of work must be discarded rather than retried with a dirty tracked context. No automatic normalization, default-template activation, version retries or profile selection is introduced.

PostgreSqlSchema version 1 creates the initial model, RLS policies and triggers in a single advisory-locked transaction, only in empty local taskmetricai_dev/taskmetricai_test databases. The operator never adopts unrelated existing tables, drops databases, or migrates automatically at request/startup. Subsequent schema changes require a new explicit migration; this initial installer is not a general migration engine. Installation registration/initial administrator bootstrapping is an operator-only transactional library operation, not a public registration API.

SQLite in-memory relational tests cover fast application/isolation regressions. PostgreSQL 17 integration tests cover provider-specific RLS, constraints, triggers and concurrency. Missing PostgreSQL configuration is reported as skipped coverage, never as successful live verification. All six PostgreSQL cases executed locally with zero skips using an outside-Git connection/passfile reference. This is synthetic local verification, not deployed credential separation or live Atlassian authorization.
